# Process overview

My response to the provided problem statement is a collaborative music environment where users can input their ideas via either a visual step sequencer or a Strudel text editor. The primary objective of this design is to provide users with a way to engage easily in order to start creating, but also to allow for more sophisticated musical expression.

In terms of this first version, the software utilizes Node's built-in HTTP server along with SQLite for storing visitor identity and contributions, including the code from which the grid is derived. This is to limit the size of the server so that it fits within the constraints of the provided Fly machine. In addition, persistent data will reside on the mounted volume. The server will store contributions/visitor identity and the intended audio evaluation will occur locally in each browser. The first server/storage implementation is documented in [0d50507](https://github.com/comp4020-agentic-coding-studio/comp4020-final-adeeth101/commit/0d50507).

The implementation separates storage, visitor identity, and routing/interface logic from musical rule logic. The module/HTTP contract was documented in [40019b8](https://github.com/comp4020-agentic-coding-studio/comp4020-final-adeeth101/commit/40019b8) with additional validation implemented in [3cf0498](https://github.com/comp4020-agentic-coding-studio/comp4020-final-adeeth101/commit/3cf0498). A restart test verifies that upon returning after a server restart, a previous visitor maintains their identity/contribution across restarts: [ce24434](https://github.com/comp4020-agentic-coding-studio/comp4020-final-adeeth101/commit/ce24434).

The primary musical design choice is to treat code as the single source of truth and to generate the grid only based on patterns understood by the grid. Any unsupported code will remain as text-only. The pattern mapping and tests are documented in [4e4a6c3](https://github.com/comp4020-agentic-coding-studio/comp4020-final-adeeth101/commit/4e4a6c3).

Currently, all local implementation checks pass; however, an audible music experience and deployed verification are required before I can confirm that the intended music interface functions correctly.

I made significant changes to the project since last time by moving away from a step sequencer style composer and to three different methods for creating the same music. These include scratch-style block-based editing, strudel-style code writing, and instrument-based block selection. In addition to those, I created separate interfaces for both composing and performance/collaboration. And most importantly, I built this system so all three styles of interaction can occur together. I got ambitious and laid groundwork for orchestration, bot automation on top of manual human control

In order to achieve that, I chose a “one model, three views” software architecture. Each of the three editors interacts with the same versioned JSON tree, therefore, the generated Strudel code is a view of the data and not a conflicting source of truth. I also made sure round-tripping would fail to an error if it could not happen, any unsupported code will be treated like any other non-supported text based drafts. Finally, I completely separated composition from performance. A save of a clip does not immediately send it into production and the person controlling the session is given a 30 second window to either let another person take the conductor role or extend their own.

I continued to make sure that automation remained transparent and reversible. The deterministic, seeded bots will propose the clips for use by the user, however the user must manually add them to the arrangement. Any track may opt-out of scene-following therefore no matter how many bots are arranged, they cannot override the decision of a human. For back-end functionality, I used a stable set of technologies including Node.js, SQLite, signed cookie authentication, Server-Sent Events (SSE), and Fly’s 256MB RAM limitations to ensure reliability. To secure the application I used Acorn allowlist parsing and server-side validation to protect the application from ever having to use JavaScript’s eval() method.

However, I still have some unanswered questions that I need to determine. One question is whether the Strudel scheduler can be started outside of its default cycle without resetting phases. Another is how I plan on addressing Blockly’s poor touch usability on mobile devices. As such, I need to develop a form editor alternative. Lastly, I need to test sample licensing and mobile device performance limitations.

As far as verification goes, I continue to be very strict about my methodology. Before I consider any acceptance check (M1-M3, C1-C4, P1-P4) completed, passing, or even planned I must clearly delineate each. Similarly, I must continue to maintain a solid boundary between simply knowing that my tests are passing and verifying that two browsers are indeed staying synchronised while listening.
